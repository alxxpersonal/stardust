# Codex CLI plugin for Stardust

Ship `plugin/codex/`, a Codex-native plugin bundle that gives Codex CLI users the same "stardust is the context spine" experience the Claude Code plugin gives: the Stardust MCP server, an auto-injected session-start context policy plus live workspace state, the authoring workflows as Agent Skills, and shared rules, installable in two commands.

<details>
<summary><b>Problem</b></summary>
<br>

Stardust ships a full Claude Code plugin (`plugin/claude/`) that wires the MCP server, injects a stardust-first policy plus live workspace state at session start, and exposes authoring commands (`/stardust:spec`, `/stardust:plan`, `/stardust:execute`, ...). Codex CLI users get none of that. They can run the `stardust` binary by hand, and `stardust sync` can drop rules into `AGENTS.md`, but there is no one-install bundle that makes Stardust the context spine of a Codex session. Codex has matured into a full plugin host (verified against `codex-cli 0.144.1`): MCP client, plugin plus marketplace system, lifecycle hooks that load from plugins, and Agent Skills. The gap is a Stardust-authored Codex bundle, not a Codex limitation.

</details>

<details>
<summary><b>Context and background</b></summary>
<br>

The extensibility surface was verified empirically against the installed `codex-cli 0.144.1`, not just docs. Full findings and provenance: `docs/research/2026-07-13-0102-codex-cli-extensibility.md`. The load-bearing facts:

- MCP: `.mcp.json` is byte-identical to Claude's; `[mcp_servers.<id>]` in `config.toml`; `codex mcp add <name> -- <cmd>`; `${CLAUDE_PLUGIN_ROOT}` expands in MCP command/args.
- Hooks: plugin `hooks/hooks.json` uses the same shape as Claude and DOES load from plugins (`config.toml` `[hooks.state]` tracks `warp@...:session_start` and `:user_prompt_submit`). Event names normalize `SessionStart` -> `session_start`. `${CLAUDE_PLUGIN_ROOT}`/`${CLAUDE_PLUGIN_DATA}` are exported to hook processes, so the existing POSIX scripts run unmodified.
- Skills: `SKILL.md` is `name`+`description` frontmatter plus a markdown body; a plugin ships them via a manifest `"skills": "./skills/"` pointer.
- Commands: Codex removed user-defined custom prompts, so there is no `/stardust:spec`-style namespaced, `$ARGUMENTS`-templated command. Skills are the replacement.
- Plugin: native manifest `.codex-plugin/plugin.json` (identity + `mcpServers`/`skills` pointers + an `interface` block); legacy `.claude-plugin/plugin.json` also accepted. Install: `codex plugin marketplace add <src>` then `codex plugin add <plugin>@<marketplace>`. A Claude-format plugin (`warp`) already installs and enables in Codex, proving cross-compat.

The Claude plugin's own assets are the raw material: `.mcp.json`, `hooks/hooks.json`, `hooks/session-start.sh`, `hooks/prompt-submit.sh`, `hooks/policy.txt`, `scripts/resolve-root.sh`, and `commands/*.md`.

</details>

<details>
<summary><b>Goals</b></summary>
<br>

- A Codex user installs the Stardust plugin in two commands and immediately has the Stardust MCP tools (`bundle`, `query`, `remember`, `check`, `status`, ...) available in a session.
- At session start, Codex receives the stardust-first policy and a live read-only workspace-state block, the same deterministic context the Claude plugin injects.
- The core authoring workflows (`execute`, `spec`, `plan`, `doc`, `adr`, `audit`, `status`, `refresh`) are available as Agent Skills that reuse the exact Stardust workflow bodies, adapted to Codex phrasing.
- The bundle is self-contained and installs from a local path or a Git marketplace, verified end to end against the installed `codex-cli`.
- Installation is documented completely, including the MCP-only fallback for users who do not want the full plugin.

</details>

<details>
<summary><b>Non-goals</b></summary>
<br>

- Codex subagents (`.codex/agents/*.toml`). Deferred; no Stardust subagent source exists yet.
- Codex-native scheduled tasks for the maintenance and digest crons. The Claude plugin uses Claude Code crons; the Codex path stays OS-level (cron/launchd calling `stardust cron run`), documented not automated.
- Changing the `stardust` binary or the MCP server. The MCP surface is already at parity; this spec wires it into Codex, it does not extend it.
- A published, self-serve marketplace listing. Local-path and Git-repo install only.

</details>

<details>
<summary><b>Approach</b></summary>
<br>

Ship `plugin/codex/`, a dedicated bundle mirroring the per-surface split the repo already uses (`plugin/claude/`, `plugin/obsidian/`). Layout:

```
plugin/codex/
  .codex-plugin/
    plugin.json          # native manifest: identity + interface + mcpServers + skills pointers
    marketplace.json     # local single-plugin marketplace (path locked in execution)
  .mcp.json              # {"mcpServers":{"stardust":{"command":"stardust","args":["serve","--mcp"]}}}
  hooks/
    hooks.json           # SessionStart + UserPromptSubmit (Claude-shape, Codex-normalized)
    session-start.sh     # copied verbatim from plugin/claude
    prompt-submit.sh     # copied verbatim from plugin/claude
    policy.txt           # Codex-neutralized (no <user-instructions priority="override"> wrapper)
  scripts/
    resolve-root.sh      # copied verbatim from plugin/claude
  commands/              # slash commands, transferred from plugin/claude (keep $ARGUMENTS)
    execute.md spec.md plan.md doc.md adr.md audit.md status.md refresh.md
  skills/                # same eight workflows as intent-triggered skills
    stardust-execute/SKILL.md ... stardust-refresh/SKILL.md
  README.md              # full install, both paths
```

Design decisions, each with an ADR:

1. Dedicated `plugin/codex/` bundle, not a dual-purposed `plugin/claude/` (ADR 0049). Codex reads `.claude-plugin/` too, but the command-vs-skill divergence and the native `interface` block make a clean separate bundle correct.
2. Slash commands are transferred directly, and skills are added (ADR 0050). Codex plugins support slash commands with `$ARGUMENTS` (verified: the official `codex` plugin ships `commands/*.md`), so each `commands/<name>.md` transfers near-verbatim (keep `description`, `argument-hint`, `$ARGUMENTS`; add `disable-model-invocation: false`; drop `allowed-tools`; soften ExitPlanMode/TodoWrite/native-plan-mode). The same eight workflows also ship as `skills/stardust-<name>/SKILL.md` for intent-triggered auto-invocation. Commands are the explicit user surface; skills are the automatic one. The workflow body transfers intact because it is CLI-driven.
3. Reuse the hook scripts unmodified, neutralize only `policy.txt` (ADR 0051). `session-start.sh`, `prompt-submit.sh`, and `resolve-root.sh` are env- and filesystem-driven and Codex exports the same env vars, so they are copied verbatim. `policy.txt` drops the Claude `<user-instructions priority="override">` wrapper (Codex injects hook stdout as plain developer context, so the "override" weight does not carry) and keeps the tool-neutral routing guidance, which already says "call the bundle and query tools" without hardcoding any `mcp__stardust__` name.

MCP wiring: the plugin manifest points `mcpServers` at `./.mcp.json`; the same file also documents the manual `codex mcp add stardust -- stardust serve --mcp` path for MCP-only users.

Session context: `hooks/hooks.json` registers `SessionStart` (matcher `startup|resume|clear|compact`) running `${CLAUDE_PLUGIN_ROOT}/hooks/session-start.sh`, and `UserPromptSubmit` running `prompt-submit.sh`, identical to the Claude bundle. Codex normalizes the event names and runs the scripts, whose stdout becomes session context.

Skills authoring is fanned out across Opus agents (one per command) for the adaptation pass, then assembled and validated.

Install and verification run against the real `codex-cli`: add the local marketplace, install the plugin, confirm the MCP server connects and a tool call returns, confirm the SessionStart hook output appears, confirm a skill loads.

</details>

<details>
<summary><b>Alternatives considered</b></summary>
<br>

- Dual-purpose the existing `plugin/claude/` bundle (add `skills/` + a `.codex-plugin/plugin.json` to it). Rejected: Claude would then load the skills AND the commands (duplication), and mixing two hosts' presentation metadata in one manifest is muddier than a clean per-surface bundle. ADR 0049.
- MCP-only, no plugin (just document `codex mcp add`). Rejected as the primary deliverable: it drops the session-start context injection and the workflows, which are half the value. Kept as the documented fallback.
- Skills-only, dropping the slash commands (the first draft, on a stale web claim). Rejected after verifying against `codex-cli 0.144.1`: only the standalone `~/.codex/prompts` was removed; plugin `commands/*.md` with `$ARGUMENTS` are fully supported, so the slash commands are shipped directly. ADR 0050.
- Rewrite the hook scripts for a Codex-specific JSON `additionalContext` envelope. Rejected: plain stdout already lands as context and the existing scripts run unmodified; a bespoke envelope adds drift for no confirmed gain. Revisit only if the empirical test shows stdout is dropped in `codex exec`. ADR 0051.

</details>

<details>
<summary><b>Risks</b></summary>
<br>

- Marketplace descriptor path ambiguity for a single local plugin (`.agents/plugins/marketplace.json` vs `.claude-plugin/marketplace.json`, and whether a `.codex-plugin/plugin.json` manifest pairs with either). Mitigation: lock it by installing into the local `codex-cli` during execution; write whichever path Codex accepts.
- Plugin hooks may require a `/hooks` trust approval on install, so context injection is not live until trusted. Mitigation: document the trust step in the README; verify the on-install behavior empirically.
- `SessionStart` stdout may surface only in the interactive TUI, not in `codex exec`. Mitigation: verify both; if `exec` drops it, note the limitation and rely on the interactive path plus the `AGENTS.md` static policy.
- Script drift between `plugin/claude/` and the copied `plugin/codex/` scripts. Mitigation: byte-for-byte copies plus a header note; a future `stardust` generate step can dedupe.
- `policy.txt` "override" semantics do not carry on Codex. Accepted: the deterministic steer to `stardust bundle`/`query` still lands.

</details>

<details>
<summary><b>Verification</b></summary>
<br>

End to end against the installed `codex-cli` (do not merely assert file existence):

1. JSON/frontmatter validity: `.mcp.json`, `.codex-plugin/plugin.json`, the marketplace descriptor parse (jq); every `SKILL.md` has valid `name`+`description` frontmatter (python).
2. Marketplace + install: `codex plugin marketplace add ./plugin/codex` then `codex plugin add stardust@<marketplace>` succeed and `codex plugin list` shows it `installed, enabled`.
3. MCP: after install (or `codex mcp add stardust -- stardust serve --mcp`), `codex mcp list` shows `stardust`, and a non-interactive `codex exec` prompt that calls a Stardust tool (for example asks it to run the `status` tool) returns real output.
4. Hooks: a fresh Codex session (TUI or `exec`) shows the injected policy and the `<workspace-state>` block, or the `[hooks.state]` entry for the Stardust session-start hook appears in `config.toml`; the `/hooks` trust state is captured.
5. Skills: at least one `stardust-*` skill is listed/loadable in Codex.
6. Cleanup: uninstall (`codex plugin remove`, `codex plugin marketplace remove`, `codex mcp remove stardust`) leaves `config.toml` clean, so the verification does not pollute the user's Codex.
7. Regression: `go build ./...` and `go test ./...` stay green (only relevant if the optional agentsync task is done).

Be adversarial: try an uninitialized workspace (the hook must degrade quietly), a missing `stardust` binary (graceful pointer), and a second install (idempotent).

</details>

<details>
<summary><b>Out of scope</b></summary>
<br>

Codex subagents, Codex-native crons, changes to the `stardust` binary or MCP tools, a published marketplace listing, and Windows hook-script variants (the bundle is POSIX for v1; note it in the README).

</details>

<summary><b>Amendments</b></summary>
<br>

- v2 (2026-07-13): Slash commands moved from Non-goals into scope. The first draft dropped them to skills on a secondary web claim that Codex removed custom prompts. Verifying against `codex-cli 0.144.1` showed only the standalone `~/.codex/prompts` mechanism was removed; plugin `commands/*.md` with `$ARGUMENTS` are fully supported (the official `codex` plugin ships them). The bundle now ships both `commands/` (explicit slash surface) and `skills/` (intent-triggered). ADR 0050 rewritten accordingly.
- v2 (2026-07-13): Open questions resolved during the build, verified against the installed binary:
  - Marketplace path: `codex plugin marketplace add ./plugin/codex` discovers `.claude-plugin/marketplace.json` and the plugin installs from a `.codex-plugin/plugin.json` manifest. `codex plugin add stardust@stardust-codex-local` reports `installed, enabled`.
  - MCP: installing the plugin registers the `stardust` server; `codex mcp list` shows it, and a `codex exec` run reached `mcp: stardust/status (completed)` returning the real index note count (115). The `internal/mcp` roundtrip test passes.
  - Hooks: plugin `SessionStart`/`UserPromptSubmit` hooks load. New command hooks require a one-time `/hooks` trust (or `--dangerously-bypass-hook-trust` for automation); once trusted, the model sees the injected `stardust-context-policy` (confirmed by having it quote the policy's opening words). Status was verified as marked-for-trust rather than auto-trusted.
  - `SessionStart` stdout reaches the model in `codex exec` (not TUI-only).
  - The verification install was fully removed; `~/.codex/config.toml` was left clean.

</details>
